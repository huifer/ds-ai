背景

当前 `.github/workflows/docker-publish.yml` 仅监听 `main`，构建后调用单个、硬编码的 Dokploy webhook。现有流程无法清楚区分测试环境与生产环境，也缺少统一的 Git Tag、容器镜像 Tag、发布审批和回滚规范。

需要建立两套相互隔离的部署环境：

- **测试环境（test）**：用于功能验收、冒烟测试和发布候选验证。
- **生产环境（production）**：用于正式对外服务，只允许经过测试的版本进入。

Dokploy 将提供两个独立应用及两个访问地址。实际 URL 和部署 webhook 必须通过 GitHub Environments / Secrets 配置，不能硬编码到仓库。

目标

- GitHub Actions 能分别构建、发布和触发 Dokploy 测试/生产部署。
- 仓库形成唯一、明确的版本 Tag 标准。
- 同一版本可以追溯到 Git commit、GHCR 镜像 Tag 和镜像 digest。
- 生产发布必须使用已经在测试环境验证过的同一 commit / 镜像 digest。
- 测试与生产的域名、密钥、数据库和第三方服务配置相互隔离。
- 任一环境可以通过不可变 Tag 快速回滚。

分支与版本 Tag 规范

1. 日常测试部署

- 推送到 `preview` 分支时，自动构建并部署到测试环境。
- 生成以下 GHCR 镜像 Tag：
  - `test`：测试环境当前版本的浮动别名。
  - `sha-<short-sha>`：不可变版本，例如 `sha-f06f9c8`。
- `test` 只能用于表示“当前测试版本”，不能作为审计或回滚的唯一依据；回滚必须使用 `sha-<short-sha>` 或明确的 RC Tag。

2. 测试候选版本

- 测试候选使用 SemVer 预发布 Tag：`vMAJOR.MINOR.PATCH-rc.N`。
- 示例：`v1.4.0-rc.1`、`v1.4.0-rc.2`。
- RC Tag 必须指向已经进入 `preview` 并成功部署到测试环境的 commit。
- 生成以下 GHCR 镜像 Tag：
  - `v1.4.0-rc.1`
  - `sha-<short-sha>`
  - 更新浮动别名 `test`
- RC Tag 只触发测试环境部署，不得触发生产部署。

3. 正式版本

- 正式发布使用标准 SemVer Tag：`vMAJOR.MINOR.PATCH`。
- 示例：`v1.4.0`。
- 正式 Tag 必须：
  - 从 `main` 上已合并的 commit 创建；
